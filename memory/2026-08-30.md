# 2026-08-30 — Newsletter Backfill

Fills gaps in the newsletter corpus from a publication's own web archive. Gmail is the
ingestor's only source, so anything that never arrived as an email — a back catalogue we
subscribed to late, posts published after an author changed platform, web-only articles —
was previously unrecoverable.

## Live case

`Joan Westenberg` (`Label_1282196755308728004`). The sender history in the DB records the
migration path: `westenberg@ghost.io` → `westenberg@mail.beehiiv.com` →
`joan@joanwestenberg.com` → `jawestenberg@substack.com`. Email delivery stops after
2026-06-06 ("Update: ending paid subscriptions, + Substack").

Scan result: **113 listed, 27 already held, 86 missing.** All 27 matches were exact
normalised-title hits; a control pass feeding 73 real DB subjects back through the matcher
matched 12/12, so the rules are not merely permissive.

## Two traps found while probing, and what they forced

1. **`?offset=` is silently ignored.** Substack's HTML archive accepts `?offset=12` and
   returns page 1 again — no 404, no redirect. `verify_pagination` measured
   `new_on_page_2: 0`. Pagination therefore terminates on *no new URLs*, never on an empty
   response, and `ListingConfig` rejects a template lacking the placeholder its pagination
   type substitutes.
2. **A short page is not the end of the archive.** Substack returns short pages mid-archive;
   an early manual probe that broke on `len(page) < page_size` truncated 113 articles to 23.

Together these are why the mapping schema carries a *listing mode* rather than only
selectors: `curl` sees 12 posts, the rendered DOM 24, the JSON endpoint all 113.

## Design

- **Three listing modes.** `html` (static + CSS selectors), `json` (listing endpoint +
  dotted paths — preferred where available), `rendered` (Playwright scroll, optional
  `rendered` extra, lazily imported).
- **Separate `data/backfill.db`.** Backfilled articles in `messages` would be picked up by
  `run_convert_pending` (raw paths point nowhere) and reset by `retry_failed`.
  `gmail_ingestor.db` is opened read-only; a test asserts it is byte-identical after a run.
- **Output produced by gmail-ingestor's own writers.** `MarkdownConverter` /
  `MarkdownWriter` / `RawEmailStore`, so the format cannot drift and the YAML backslash-
  escaping fix applies for free. Only `source_url` + `origin` are injected.
- **IDs are `web-<sha256(canonical_url)[:16]>`.** No underscore (ingestor-tools splits on
  the last one), no path characters (find_raw_files rejects them), visibly distinct from
  16-hex Gmail IDs. Canonicalisation drops query strings so `?utm_source=` cannot mint a
  second ID.
- **Title matching, never dates.** Exact normalised slug → prefix (catches Substack's
  truncated URL slugs) → `difflib` ≥ 0.90. Delivery and publication timestamps differ by
  hours.

## Verified downstream

- `ingestor-tools`: `yaml.safe_load` OK, `id` stays a `str`, `extract_message_id` and
  `find_raw_files` both resolve; the real organizer produced one directory per email across
  a mixed `web-`/Gmail tree with no warnings.
- `newsletters-web`: hand-rolled front-matter parser OK, `parse_date` OK,
  `collect_emails()` returned 3/3 records with zero `ambiguous`/`unusable`.

## Impact

No schema change and no writes to `gmail_ingestor.db`. Two additive front-matter keys on
backfilled files only. `newsletters/{label}/` gains `web-…` directories — functionally fine,
but both sibling ARCHITECTURE.md files stated the directory name *is* a Gmail message ID, so
each got a short note. That was the only change outside this repo, and it was documentation.

## Notes

- The CLI lives at `ingestor_tui.backfill.cli` rather than `scripts/backfill_cli.py` as
  planned — the repo has no `scripts/` directory, and a console script needs an importable
  module.
- `origin` is written quoted (`origin: "backfill"`) because provenance values go through the
  converter's `_escape_yaml`. Both downstream parsers read it as the string `backfill`.
- `pyyaml` is a **dev** dependency only: tests use it to assert the output parses the way
  `ingestor-tools` parses it. Production code never parses YAML.
