## The bug

Paging the endpoint by hand, `limit=50` returned 23 items at `offset=0` and 35 at
`offset=50` — 58 of 85. Substack's `/api/v1/archive` caps `offset=0` at **23 posts for any
`limit`**, and returns the full `limit` at every other offset (checked on all four
publications in use). `listing._page_urls` strode by `page_size`, so posts 23–49 were
never requested. No error, and a non-round total that looked complete.

It had been silently costing the existing mappings too:

| Label | Before | After |
|---|---|---|
| Dharmesh Ba | 58 listed / 56 missing | 85 / 83 |
| Joan Westenberg | 119 / 9 | 145 / 28 — all of July 2026 was in the gap |
| Neel Chhabra | 30 / **0** | 44 / 14 — pre-rebrand archive is 37 posts, not 23 |

The 2026-09-12 note that Neel's label was "complete" was wrong because of this.

**Fix:** `_read_json` now runs its own offset loop and advances by `len(items)` (raw count,
pre-dedup). Page/none pagination and all HTML modes are unchanged — HTML item counts are
selector matches, not server counts. Item-array extraction moved into `_json_items`.

**Why the tests missed it:** fixtures mapped literal URLs to responses and could describe
an impossible server. The old `test_json_short_page_does_not_stop_pagination` encoded the
bug — `offset=0` → 1 item, `offset=2` → items 2–3. Added `FakeOffsetApi`, which slices
one fixed catalogue, plus 3 tests (gap reproduction with exact request sequence, non-zero
`start`, page-type unaffected). Terminator URLs in runner / multi-source / listing
fixtures moved from `offset=page_size` to `offset=<items received>`.

261 tests pass (3 new). Touched files ruff-clean.
